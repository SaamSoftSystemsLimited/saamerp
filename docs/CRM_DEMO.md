# Customers, contacts and quotations — implementation slice

## What works

- Create/list customers with a demo branch and optional validated email.
- Create/list contacts belonging to a customer. A contact cannot be attached to a
  quotation for a different customer.
- Create multi-line quotation drafts, calculate exact NGN totals in integer kobo,
  issue a snapshot, and record acceptance or rejection. Whole quantities only.
- Transition DRAFT → SENT (displayed as Issued) → ACCEPTED or REJECTED.
  Repeating the current transition is idempotent; terminal states cannot be reopened.
- Preserve customer/contact names and lines in issued quotations. Issuing does not
  send email. Downloadable HTML is a synthetic quotation document, not an invoice.
- Filter demo records by branch; browser-local edits survive reload. Reset restores
  the generated synthetic dataset after explicit confirmation.

This is a narrow, partial CRM-001 slice. Leads, orders, contracts, renewal billing,
customer/contact editing and archive, quotation revision, tax, document numbering
policy, real identity/membership permissions and specialist acceptance remain open.
Do not mark the CRM epic Done. No tax rates are assumed.

## PostgreSQL and API

PostgreSQL 17 is used for the isolated runner/local demo. It is a supported major
release (https://www.postgresql.org/support/versioning/). Flyway applies
`V1__crm.sql` on startup of the `postgres` profile. SQL uses tenant-scoped composite
keys, customer/contact foreign keys, range checks and transaction-scoped writes.
Quotation status changes lock the quotation row and append a database event.

This database is a demo schema, not a decision to replace the proposed
database-per-customer SaaS architecture. Fifty-customer provisioning, pool budgets,
selective restore, production audit and branch authorization remain unproven.
The API fixes tenant identity to one synthetic workspace; it does not trust a
caller-supplied tenant ID. Service/database isolation is tested with other tenants.

The `postgres` profile binds to loopback and requires an explicitly supplied demo
password of at least 16 characters. HTTP Basic protects the API for runner scripts.
This is a single demo administrator, not production authentication, MFA or RBAC.
No CORS connection from the public Pages site is configured. Never expose this
profile with customer data. The default profile still denies business HTTP requests.

Environment variables:

- `CRM_DATABASE_URL`: JDBC PostgreSQL URL.
- `CRM_DATABASE_USER`, `CRM_DATABASE_PASSWORD`: isolated database credentials.
- `CRM_DEMO_PASSWORD`: temporary API password; the exporter generates its own.
- `SPRING_PROFILES_ACTIVE=postgres`: opts into the local/runner API.

API under `/api/demo/crm` (authenticated as `demo`):

| Method | Path | Result |
| --- | --- | --- |
| GET | `/` | Demo customer/contact/quotation dataset |
| POST | `/customers` | Create customer; derive ID server-side |
| POST | `/contacts` | Create contact after customer ownership check |
| POST | `/quotes` | Create draft; calculate total server-side |
| POST | `/quotes/{id}/status` | Issue/accept/reject with row lock and event |

Invalid input returns 400; unknown/foreign records return 404; forbidden transitions
return 409; missing or wrong credentials return 401. Request-supplied totals are not
used. Limits are 100 lines, quantity 1–10,000, positive unit prices with two decimal
places and a bounded safe total. Dates use UTC calendar dates.

## GitHub runners → GitHub Pages

1. A GitHub-hosted Ubuntu job starts its own PostgreSQL service.
2. The Java build runs module, HTTP-security and real PostgreSQL integration tests.
3. `scripts/verify_crm_demo.py` starts the packaged Java app, creates synthetic
   customers/contacts/quotations through authenticated API requests, and exports
   the fixed demo tenant only.
4. The script stops/restarts Java and asserts that PostgreSQL returns the identical
   records and issued quotation snapshot after restart.
5. The resulting `apps/web/public/demo/crm.json` is bundled into the static frontend.
6. TypeScript, unit and Chromium end-to-end tests run before Pages deployment.

The Pages site fetches a relative `demo/crm.json` asset. Browser edits stay in
localStorage; they are not written to PostgreSQL, shared with other visitors, or
stored in the repository. Runner databases disappear after the job. Credentials,
other tenants' test records, and database dumps are never published. The committed
fixture was generated by the same real API for local development and frontend CI.

When opening a newer deployment, an existing browser-local dataset remains intact.
Use Reset demo to load the latest seed. Only synthetic examples belong in this site.

## Local reproduction

Use `deploy/compose.demo.yml` for an isolated PostgreSQL database. Supply a local
`CRM_DATABASE_PASSWORD`, then `docker compose -f deploy/compose.demo.yml up -d`.
Configure the JDBC URL `jdbc:postgresql://127.0.0.1:55432/saamerp_demo`, user
`saamerp_demo`, and that password. Build with JDK 21:

```sh
cd apps/backend
# Supply CRM_TEST_DATABASE_URL, CRM_TEST_DATABASE_USER and CRM_TEST_DATABASE_PASSWORD.
./mvnw --batch-mode --no-transfer-progress clean verify
cd ../..
# Supply CRM_DATABASE_URL, CRM_DATABASE_USER and CRM_DATABASE_PASSWORD.
python scripts/verify_crm_demo.py \
  --jar apps/backend/target/saamerp-backend-0.1.0-SNAPSHOT.jar \
  --output apps/web/public/demo/crm.json
cd apps/web
npm ci
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

The exporter requires a fresh synthetic tenant; it refuses to overwrite an existing
one. Do not clear an existing business database to rerun it. PostgreSQL tests are
explicitly skipped if `CRM_TEST_DATABASE_URL` is absent; CI supplies it and must run
all four integration tests. Local verification recorded six backend tests with
zero skipped, eight frontend tests, and an API export/restart check.
